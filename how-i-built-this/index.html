How I built this site

Four months of attempts that didn’t stick, then one afternoon once the content was right. This is the whole process, including the parts that didn’t work.

I made the calls: what the site is for, what it says, what stays and what goes. Claude was the tool I worked with: it drafted, mocked, reviewed and packaged changes, and Claude Code shipped them. This page is written from my working sessions.

  • < 6 hrsfirst real draft to live site
  • 15homepage versions in one day
  • 10visual directions, 9 rejected
  • 6handoff kits to Claude Code

Four months of on-and-off attempts. Then one day, Nov 13: v1 at 10:50 a.m., twelve versions by 12:30, live that afternoon. Every change since is public on GitHub ↗

01Where it started

The site has lived on GitHub since May 2025. In May 2026 I rebuilt it in an evening with Claude Code: the first pull request merged at 6:24 p.m., and four more landed within a day, through a staging branch into production. Then I turned it into an experiment: a PM agent that compared the site to others and wrote a PRD, an engineer agent that built it, and a QA agent that checked the code against the PRD.

The pipeline worked. The site didn’t say much. It was a dark page that mostly repeated my resume, and nothing on it showed how I actually work.

03Content first, design last

In November I went back through every conversation about the site and asked Claude to consolidate them. The pattern was obvious once it was written down.

Why nothing stuck

  1. 1Designing before there was content. Every mockup was filled with placeholder copy. Generic words in a generated layout read as generated, whatever the palette.
  2. 2The story kept moving. It shifted from “fintech PM” to “AI-forward PM” to “builder,” and each shift made the last design wrong.
  3. 3The only goal was a negative one. “Doesn’t look AI-made” is a list of things to avoid. You can’t converge on a list of things to avoid.

The plan

  1. Step 1Lock three decisions: the site’s job, the direction, and how much of my day job to show.
  2. Step 2Inventory real artifacts: what I’ve built, and what proof exists for each (repo, live link, screenshot).
  3. Step 3Write every word in plain text, with no design at all.
  4. Step 4Design around the finished text. One mockup, not three.

That pushback became the line at the top of How I work: I build proofs of concept before PRDs. The prototype, and the conversation that built it, is the spec.

04Real facts only

Before any design, every fact on the page needed a source.

  1. GitHubPulled the commit history of every public repo and the private Tempus log. Commit counts, dates, merged PRs and issue numbers on this site come from there.
  2. ResumeCareer dates, titles and outcomes come from my master resume, word for word where possible.
  3. SessionsProcess notes, wins and losses come from the working sessions where each thing was built, not from memory.

The rule: if a number or a claim can’t be traced to one of those three, it doesn’t go on the page. A few things I wanted to say came out because I couldn’t source them.

07How a change gets made

Every change on this site went through the same loop, whether it was a favicon or a full rebuild.

  1. 01TalkI describe the change and what’s wrong with the current one.
  2. 02MockClaude mocks options side by side on the canvas, usually three.
  3. 03PickI choose, combine or reject. Often I reject.
  4. 04ReviewA design review skill checks it before it’s done.
  5. 05PackageThe change becomes a small kit: spec, working reference, prompt.
  6. 06ShipClaude Code plans, I approve, it builds, I deploy.

The review skills

  1. critique/design:design-critique. Run twice. The first pass caught the Builds layout breaking at desktop width, the second caught the top bar eating a quarter of a phone screen.
  2. system/design:design-system. Scored the page 64/100 with 14 issues: 9 colors hardcoded 202 times, 19 different gap values, buttons with no hover or focus states. Fixed in one pass.
  3. elevate/design-skills:design-elevation. I kept five of its moves and skipped five that fought the direction, like switching the font to Inter and adding gradients.

The handoff kits

  1. HomepageThe full rebuild: design spec, tokens, every word of copy, decisions, and a working reference page.
  2. Journey“2024 → now”, the live dot, and the “More to come!” arrow.
  3. FaviconThe Geist M with a pencil underline, at every size browsers and phones ask for.
  4. Top barThe same mark, left of my name.
  5. IntroThe intro line that edits itself.
  6. This pageThis build log.

Every kit’s prompt says the same four things

  1. Read the spec and the reference, then find the part of the site it touches.
  2. Tell me the plan in a few lines and wait for my go.
  3. Change only that part, with the site’s existing tokens.
  4. Keep the kit out of git. The repo is public; the kit is mine.

Inside every Claude Code session: project-kickoff

project-kickoff is a Claude Code skill I built. One command sets up a new project with the docs, commands and guardrails below, scaled by tier: a Utility gets less paperwork than an App, and an App less than a Platform.

├── README.md
├── CLAUDE.mdrules every session reads first
├── LICENSE
├── docs/
│   ├── PRD.mdwhat and why
│   ├── ROADMAP.mdphases and build order
│   ├── RATIONALE.mdthe why behind the non-obvious rules
│   ├── DESIGN.md
│   ├── DATA-MODEL.md

│   ├── workflow.mdthe issue → PR → merge loop
│   └── commands.mdcheat sheet for the commands
├── .claude/
│   ├── settings.jsonstanding permissions, e.g. Bash(git:*)
│   └── skills/the seven commands
└── .github/
    ├── ISSUE_TEMPLATE/App and Platform tiers
    └── PULL_REQUEST_TEMPLATE.md

Seven commands run the work

  1. /start {issue}Loads the issue, branches (or resumes the branch), reads only the docs the change needs, builds, reviews its own work against the acceptance criteria, runs the checks, commits with real reasoning and opens the PR. Can take several small related issues at once.
  2. /merged {pr}Confirms the merge with GitHub’s API, deletes the branch, closes out the issue, files any follow-ups, and writes the cycle to the project’s audit log.
  3. /promoteOpens the PR from dev to production. I merge it and tag the release myself.
  4. /new-issueTurns a rough note into a real issue: acceptance criteria, milestone, owner label.
  5. /batch-issuesWorks several clear, small issues back to back. Every one still gets its own PR and my merge.
  6. /audit-docsRead-only. Checks the docs and the commands against about 19 known ways they drift or break.
  7. /commandsLists the project’s commands, live.

From issue to production, on this site

  1. 01IssueAnything bigger than a couple of prompts gets one, with acceptance criteria.
  2. 02Branch/start branches off stage: feature/{issue}-{slug}.
  3. 03BuildOne issue per session, against the docs.
  4. 04PRInto stage, with the PR template’s checklist filled in.
  5. 05Checkgit diff --check on the staged changes, then layout by eye on a Netlify preview at 375, 768, 1280 and 1440px.
  6. 06MergeI merge. Always me.
  7. 07Sync/merged verifies, cleans up and logs.
  8. 08Promotestage → main. GitHub Pages builds production from main; I tag the release.

Red rules mark the two steps only I can do.

The safeguards

  1. InvokeEvery command with a side effect is set to disable-model-invocation: true. Nothing runs unless I type it.
  2. MergeNo PR merges without me. One setting lets the work move faster (bundling small issues, batch runs), and it still can’t turn the merge gate off.
  3. ChecksThe kit runs typecheck, lint and tests in CI on projects that have them. This site has no build or test tooling by design, so its one automated check is git diff --check, run on the staged changes. Layout is checked by eye on a preview at four widths.
  4. Scopesettings.json pre-approves routine git and GitHub commands, like git commit and gh pr create, so sessions don’t stall. It explicitly denies git push --force, git reset --hard, git clean -fd and rm -rf. Merging isn’t on the list at all.
  5. ReleaseProduction is its own step. Feature PRs go into stage; /promote opens stage → main, and I tag each release by hand because the tag is the rollback point.
  6. Truth/merged checks merge state with GitHub’s API, not local git, after a real bug where local state lied.
  7. RecordA permanent audit-log issue gets an entry every cycle. Findings tagged “kit candidate” go back into project-kickoff itself.

How the kit got here

  1. v0.1The first kit: a tiered doc set and three commands, /start, /ship and /merged, built by auditing lantern’s docs.
  2. BugsReal use found real bugs: arguments indexed wrong, a shell-quoting failure on macOS zsh, permission grants that didn’t match the commands, and a completion record that checked the wrong GitHub resource. All fixed.
  3. /shipFolded into /start. The safety sweep lived only on /ship, and /ship didn’t reliably get run. A check only counts if it’s on a step you can’t skip.
  4. v0.2.0Seven commands, the audit log, the merge gate, a versioned changelog, and an install script that catches stale downloads. Runs in the Claude Code CLI, VS Code and claude.ai.

09Calls I made

Plenty of good ideas didn’t make it. These are the ones that shaped the page.

+ Kept

  • Content before design, every time.
  • One hand-drawn mark per idea: an underline, a redaction, a circle, a highlighter, a margin note.
  • Red only means “new”: new words, current role, my mark. Strikes are graphite.
  • Every Build gets a “Didn’t” list. Admitting what failed reads as a person.
  • Claude is credited as a tool I used, not the builder.

− Cut

  • Commit charts per project, then one combined chart. Numbers without a story.
  • A full-width black band for How I work. It broke the page.
  • A five-row index at the top of Builds.
  • A uniform button system. Reverted the same hour.
  • Funny Claude “reviews” of working with me.
  • A “Here now” line under my current role that I never asked for. Cut on sight.

10Two details

The mark

  1. LetterThe M is Geist SemiBold, the same face as my name and headings, traced from the font file into a shape so it renders the same in every browser.
  2. MarkThe red pencil underline from the homepage thesis, so the mark and the page share one gesture.
  3. 16pxThe underline is drawn thicker in the smallest favicon so it doesn’t disappear in a browser tab.

The intro line

Product manager and builder in San Diego. I build prototypes and ship them with Claude. I run a technical product team in fintech. Product manager & builder in San Diego. I write PRDs build prototypes and hand them off ship them with Claude. I run a technical product team in fintech.

The intro plays once when you land: the old way of doing product gets struck through and rewritten, one edit at a time. That was the idea the whole site grew toward: a working sheet I’m still marking up.
