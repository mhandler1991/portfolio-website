01How I work

I build proofs of concept before PRDs.

A working prototype answers the questions a spec can only list, so I bring the business and engineering teams something they can use, not a document they have to imagine from. The prototype, and the conversation with Claude that built it, is the spec.

  1. 01Kickoffproject-kickoff writes the PRD, roadmap and CLAUDE.md before any code.
  2. 02IssuesWork is cut into issues small enough for one session.
  3. 03Session/start picks an issue; I build it with Claude Code against the docs.
  4. 04Review/ship opens a PR. I review it before it merges.
  5. 05ShipMerging closes the issue and deploys.

The workflow, in detail

  • CLAUDE.mdProject rules every session reads before it touches code.
  • docs/PRD.md · ROADMAP.mdWhat and why, kept separate from build order.
  • .claude/skills/start · ship · mergedPick an issue, open the PR, clean up after merge. Manual only: Claude can’t run them on its own.
  • .claude/settings.jsonStanding permissions per tool, so sessions don’t stop to ask about git.
  • The issue ruleAnything that takes more than a couple of prompts gets an issue. One at a time.
  • .github/PULL_REQUEST_TEMPLATE.mdEvery PR answers the same questions.
  • Token reportMeasures what each session loads. In lantern it cut that in half.
  • /audit-docsChecks the doc set for drift and files what it finds.

The same kit starts every project. See it in lantern’s repo ↗

A multiplayer 3D dice roller for D&D. Players join a room and roll together, with no server.

Process

I didn’t build physics or networking. The dice come from an open-source 3D dice library and the connections from Trystero, a peer-to-peer library, so the work went into the table itself. A short spike against the dice library came first, and it found three bugs in the library before any UI existed.

+ Worked

  • Spike first: library bugs surfaced before they could hide inside the UI.
  • A black-screen bug produced a boot smoke test that now runs on every build.

− Didn’t

  • The host couldn’t connect to invited players. Five rounds of diagnosis later, the relay servers I’d added to fix connectivity were the cause.
  • Die numbers read as the wrong digits in a high-contrast font at small sizes. Swapped the font.

project-kickoff

When

RepoSoon

Writes a new project’s starter docs and repo scaffolding, scaled to how complex the project is.

Process

Built by auditing lantern’s docs and turning what worked into a template. Its first real test was ClaudeAssistant, a pipeline that turns GitHub issues into draft PRs; that project’s running audit log feeds fixes back into the kit.

How it changed

  • TiersOne doc set for everything became three tiers (Utility, App, Platform), so a small script doesn’t get a platform’s paperwork.
  • SplitPRD.md split into PRD (what and why) and ROADMAP (build order).
  • LayoutDocs moved under docs/. Only README, CLAUDE.md and LICENSE stay at the root.
  • Commands/start, /ship and /merged moved from commands to skills when Claude Code merged the two, set so Claude can’t trigger them on its own.
  • WebA claude.ai version, which has no git access: it writes the same files plus a setup script to run locally.

+ Worked

  • The same doc set now starts every project, in the CLI, VS Code and claude.ai.
  • Its first real project, ClaudeAssistant, merged 14 PRs in its first week.

− Didn’t

  • Argument placeholders broke in lantern’s commands. The kit now confirms how arguments are read before relying on them.
  • The first doc audit on that project found three problems in the kit’s own docs.

doc-tailor

Type
Claude skill
Status
In daily use
Reads
Master document, fact bank (Google Drive)
Sample runSoon

Tailors a master document to a specific brief. It scores the fit first, then rewrites using only facts I’ve approved, and checks the result stays within its page limit.

How it got here

  1. v0by handI pasted document versions into chat and got edits back. Across 63 older versions, facts conflicted and numbers had drifted between sections.Gain: Showed the real problem: the source material, not the editing.
  2. v1first skillOne master document and one fact bank. The skill may only select and rephrase from the bank. Cost: every page check exported a PDF into the conversation, about 100K characters each.Gain: Nothing invented: every line traces back to an approved fact.
  3. v2lighter checksA script estimates page length from the saved doc, and the PDF exports once, at the end. The Google Docs rules it needs are built in instead of loading a 15 to 20K-token skill.Gain: Page checks went from one PDF per check to one per run.
  4. v2.1currentScores the fit first and stops. Nothing is copied or edited until I reply go.Gain: Low-fit requests stop before any work starts.

Why it landed here

Two rules carry it. A closed fact bank means the model can rephrase but can’t invent. The scoring gate means low-fit requests stop before any work starts.

+ Worked

  • Every tailored version traces back to an approved fact.
  • Low-fit requests stop before any document is copied or edited.

− Didn’t

  • An install dropped the page-length script, and several runs quietly fell back to estimates until I repackaged it.
  • The score measures fit on paper, not the outcome. It can’t see context that isn’t in the documents.
